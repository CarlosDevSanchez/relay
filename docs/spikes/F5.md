# F5 spike: Codex CLI (codex-cli 0.164.0, macOS arm64)

## 0. Install and method
- Official channels (github.com/openai/codex README; `brew info --cask codex` shows homepage github.com/openai/codex, `npm view @openai/codex` the same repo): `brew install --cask codex` or `npm i -g @openai/codex`.
- Ran exactly: `brew install --cask codex` -> `codex-cli 0.164.0` at `/opt/homebrew/bin/codex` (-> `/opt/homebrew/Caskroom/codex/0.164.0/bin/codex`, a native binary). npm latest was also 0.164.0 (brew's metadata said 0.163.0 before the install fetched 0.164.0).
- No login was done; `~/.codex` and `auth.json` were never touched or read. Every probe used a temp `CODEX_HOME`.
- To get real transcripts without an account: a temp `config.toml` with a custom model provider (`model_provider="stub"`, `[model_providers.stub] base_url="http://127.0.0.1:<port>/v1" wire_api="responses" env_key="STUB_KEY" supports_websockets=false`) pointing at a local stub server that answers the Responses SSE stream (`response.created` / `response.output_item.done` / `response.completed`) or HTTP 429 `{"error":{"type":"usage_limit_reached","message":...,"plan_type":"plus","resets_at":...}}`. `codex exec` and the real TUI (driven through a pty) both ran against it, so transcript shapes below are the real CLI's, with a fake backend. The server-side 429 body is **our guess** of the real one (see 6).
- Codex creates its state on first run inside `CODEX_HOME` (SQLite DBs `state_5.sqlite`, `logs_2.sqlite`, ..., `installation_id`, `shell_snapshots/`, `skills/.system`, `thread-writer-locks/`, `.tmp/plugins` (a plugin-marketplace sync), `tmp/`). Even `codex login status` creates `tmp/`. So Relay only runs the status probe on imported Codex homes that already have `config.toml`, `installation_id`, `state_*.sqlite` (names only) or `sessions/` (never stat'ing `auth.json`); others show "sin comprobar". Managed homes are always probed.

## 1. Config dir
- `CODEX_HOME` (shown by `codex doctor`, accepted by every command). Default `~/.codex`. `config.toml` `cli_auth_credentials_store` defaults to `"file"` (string table of the binary), i.e. credentials are `$CODEX_HOME/auth.json`, so `CODEX_HOME=~/.codex` is the same install as plain `codex`. Relay therefore sets `CODEX_HOME` for every account, including the default one (no Claude-style quirk); `isDefaultInstall(dir, home, 'codex')` is informational only. A keyring-backed store (`cli_auth_credentials_store="keyring"`) would key the secret by path; unverified, Relay never changes it.
- Env vars the binary knows that would override an account's own login: `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN` (+ `CODEX_THREAD_ID`, session-scoped). Relay strips them from the environment it passes (`env.ts`).

## 2. Login / status / logout
- `codex login [--with-api-key | --with-access-token | --device-auth]`, `codex login status`, `codex logout`. Plain `codex login` is the browser OAuth flow (not run here: it would open the user's browser). **Unverified**: its terminal output and whether a code has to be pasted (Relay's Codex login panel has no code box; the real terminal stays under "Ver terminal").
- `codex login status` (verified, fresh home): stdout empty, stderr `Not logged in`, **exit code 1**. The logged-in text is `Logged in using ChatGPT` (also `... using an API key` variants) in the binary's strings; exit 0 is the natural counterpart but **unverified** without an account. It prints no email or plan, so Relay's Codex cards show only "sesión iniciada" / "sin sesión" / "estado desconocido". Relay: exit 0 = logged in, exit 1 = not, anything else (including a missing binary) = unknown.
- `codex doctor [--json]` exists (redacted report incl. auth state); not used.

## 3. Resume
- `codex resume [SESSION_ID] [PROMPT]` (`--last`, `--all`, picker by default); `codex exec resume <id> <prompt>` is the non-interactive one. `SESSION_ID` = UUID or session name.
- Verified with the stub backend: a rollout **copied** into a different `CODEX_HOME` (no SQLite index copied) is found by id: `codex exec resume <id> "continue now please"` replayed the whole history to the model; the real TUI (`codex resume <id> "tui resume prompt xyz"` in a pty) sent the positional prompt as the first new user turn. So an initial prompt is supported with the same argv shape as Claude: `['resume', id, message]` (message a single argv element; Relay's `checkContinueMessage` rules apply: no leading `-`, not a single ASCII word).
- The resumed rollout is appended in place.

## 4. Sessions on disk
`<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-YYYY-MM-DDThh-mm-ss-<session-id>.jsonl` (local time in dirs and name; the id is a UUIDv7, 36 chars, accepted by `isSessionId`). Plus a SQLite `threads` table in `state_5.sqlite` (id, rollout_path, cwd, title, first_user_message, ...), which Relay does not read or write.
- Line 1: `{"timestamp","ordinal":0,"type":"session_meta","payload":{"session_id","id","timestamp","cwd","originator","cli_version","source","model_provider","base_instructions":{...~20 KB...},"history_mode":"paginated",...}}`. The first line alone is ~20 KB, so Relay reads 64 KB for `session_meta` of every rollout and up to 512 KB (title) only for those of the listed project.
- Every line `{"timestamp": ISO8601, "type": "session_meta" | "event_msg" | "response_item" | "turn_context" | "world_state" | "token_usage_record", "payload": {...}}`.
- First user message (the title): `event_msg` with `payload.type == "item_completed"` and `payload.item.type == "UserMessage"` -> `payload.item.content[].text` (type `text`). Not the `response_item` user messages: the first ones are the injected `<environment_context>` and `# AGENTS.md instructions for ...` wrappers. A legacy `payload.type == "user_message"` / `payload.message` shape is also accepted (unverified: only seen in older versions).
- cwd = `session_meta.payload.cwd` (realpath, same as the project path); timestamps per line; file mtime is used for "hace X".
- A `codex exec` session has `originator: "codex_exec"`, `source: "exec"`, `thread_source: "user"` (verified on disk); the real TUI (verified on a temp CODEX_HOME) `originator: "codex-tui"`, `source: "vscode"`, `thread_source: "user"` (the IDE extension is `codex_vscode`); Relay lists top-level threads of either. Multi-agent (0.164) child threads are separate rollouts of the same cwd: from the binary's strings `source` is an object (`SubAgentSource`: `thread_spawn{parent_thread_id,depth,agent_nickname,agent_role}`, `review`, `compact`, `memory_consolidation`) and `session_meta` may carry `parent_thread_id`, `forked_from_thread_id`, `subagent_kind`. **Not verified with a live spawn_agent run** (the stub backend was not scripted to call it). Relay treats a rollout as top-level only when `source` is a plain string, `thread_source` is absent or "user" and there is no parent id; only `originator: codex-tui` top-level rollouts may bind a tab. Rollouts without `source` (very old Codex) are not listed or bound. Residual window: a TUI started outside Relay in the same `CODEX_HOME` + cwd before the tab's first prompt is indistinguishable. The TUI creates the file with the first turn (it was not observed to exist before the first prompt).
- Successful turn tail: `response_item` (assistant) -> `token_usage_record` -> `event_msg token_count` (`info.total_token_usage` filled) -> `event_msg task_complete`.

## 5. Handoff
Copying the rollout file to the same relative path under the target's `sessions/` is enough for `codex resume <id>` on the target (verified above). Relay reuses the Claude copy semantics (complete lines only, never overwrite, extend an older prefix by its tail, back a diverged target up as `<name>.relay-bak-<ts>`, record the copied byte range in `copies.json`). The backup name does not match `rollout-*.jsonl`, so Codex ignores it. If the target already has a rollout for that id (possibly under another date dir), that path is reused. Nothing else (SQLite, shell snapshots) is copied; there is no `file-history` equivalent to lose.

## 6. Usage limit signal
- Quota exhausted (stub 429 with `type: usage_limit_reached`): `codex exec` prints `ERROR: You’ve hit your usage limit. Upgrade to Pro (...), visit https://chatgpt.com/settings/usage to purchase more credits or try again at Dec 31st, 2029 7:00 PM.` and the rollout (exec and TUI, both verified) ends with `event_msg` `token_count` (`info: null`, `rate_limits` all null in the stub) and `event_msg` `task_complete` with `payload.error = {"message": "<same text>", "codex_error_info": "usage_limit_exceeded"}`.
- Reliable machine signal: `codex_error_info == "usage_limit_exceeded"` (from the binary's error enum, which also has `rate_limit_exceeded` = transient "try again in 5s", `quota_exceeded`, `usage_not_included`, `server_overloaded`, ...; only `usage_limit_exceeded` is treated as the quota). Reset: text after `try again at `, local time, in the formats the binary carries as strings: `%b %-d, %Y %-I:%M %p` when it is another day (stub: `Dec 31st, 2029 7:00 PM`, ordinal suffix on the day), only `%-I:%M %p` (`3:15 PM`) when it is today (bare clock time = today relative to the event timestamp, tomorrow if already past), and a year-less `%b %-d at %-I:%M %p` also found in the strings (next year if already past). All parsed by `parseCodexReset`; the same-day and year-less variants are **unverified against the real server** (the stub only produced the dated one). When it does not parse (`Try again later.`) or is absent (e.g. the message variant "You’ve hit your usage limit for <model>. Switch to another model now" has no time) the hit is still reported with `resetAt: null`; the model-specific variant is flagged `modelSpecific` and the UI shows a toast (change model) instead of the account-switch dialog.
- The `token_count.rate_limits` snapshot (`primary`/`secondary` windows with `used_percent`, `window_minutes`, `resets_at`, `plan_type`, `rate_limit_reached_type`) exists but was null with the stub; not used.
- **Unverified**: the real server's 429 body and message wording (plan-specific variants: Plus/Pro/Team/credits), and an `error` event variant at top level (the parser accepts `payload.codex_error_info` too).
- Live detection tails the rollout; the card state is derived from rollouts of the last 7 days: limited only if the newest limit event has a parseable reset in the future and no `token_count` with usage after it (lines copied in by a handoff are skipped by byte range).

## 7. Instructions / memory
- Global instructions: `$CODEX_HOME/AGENTS.md` (+ `AGENTS.override.md`; per-project `AGENTS.md` files). Verified: a **symlinked** `$CODEX_HOME/AGENTS.md` -> `~/.relay/shared`-style file is read and its text reaches the model request. Codex does not write it. Relay's Codex shared memory therefore links only `AGENTS.md` (shared copy `~/.relay/shared/AGENTS.md`, separate from `CLAUDE.md`), same consent rules as Claude. No skills/agents/commands/project-memory sharing for Codex (Codex has its own `skills/` and a SQLite `memories_1.sqlite`; not touched).

## 8. Unverified (kept conservative)
Interactive `codex login` output/flow in a pty; logged-in `codex login status` output and exit code 0; real quota wording and reset text; keyring credential store; Windows. The TUI picker's listing of a handed-off session (the SQLite index lacks it) is irrelevant for Relay because it always resumes by id.
